# F10a · 分区域管理底盘 · 讨论稿

本文是「在 finder 内建立多区域管理与交互的基础底盘」的讨论稿，不是实施计划。历史（history）只是这个底盘的第一个具体消费方——底盘立起来之后，history 是一个 trivial 的区域增量；记录端（`config.RecordDirHistory` 写 `history.json`）作为历史的数据源需要单独落地，但它的优先级降到「跟着 history 区域一起做或紧随其后」。

讨论原点：F10-访问历史.md 的「我的建议：底盘建设」一节，明确提出要抽 fileList / historyList / preview 三个自管理区域，加 session.go 调度。本文围绕该建议的几个隐含决策点展开讨论，最终产出 F10b 实施计划（对齐 F8/F9 粒度）。

## 一、现状基线（要拆出来的东西）

当前 `internal/finder/` 包结构：

- `session.go`（~900 行）：finder 全部可变状态（`finderState`） + 边框/内容/预览绘制 + 鼠标路由 + 键盘路由 + chdir/pick/activate 等命令 + 关闭路径 + git 后台查询
- `preview.go`（~170 行）：预览 state + 绘制 + 鼠标滚轮
- `model.go`、`add.go`、`delete.go`、`rename.go`、`git.go`、`strutil.go`：辅助

「区域」概念在代码里已经隐含存在：

- **文件列表区**（左栏）：`finderState.cursor / topIdx / showEntries / allEntries / pickerW / listH` + 一组方法（`drawContent` / `drawBreadcrumb` / `drawEntry` / `handleKey` / `handleLeftMouse` / `activate` / `chdirTo` ...）
- **预览区**（右栏）：`previewState` + `drawPreview` / `refreshPreview` / `scrollPreview` / `handleRightMouse`
- 没有「history 区」

文件列表区是**和 session 强耦合**的（`finderState` 直接持有其字段，session.go 整片都是它的逻辑）；预览区已经是松耦合范式（独立文件 + 独立 state + Session 方法）。底盘建设的目标：把文件列表区也按 preview 的范式拆出独立文件 + 独立 state，再加上 `historyList` 区，三个区都掛到 session 的 `regions []Region` 切片上调度。**接口层级上分为两类**（§2.6）：fileList / historyList 实现 `KeyboardRegion`（接键盘、参与 focus），preview 实现 `Region`（不接键盘、不参与 focus）。

## 二、议题 1：Region 接口形状（核心议题）

原建议随手一写的四件套：`display()` / `handleEvent()` / `focusOn()` / `focusLost()`。每个方法都有几个相互纠缠的设计选择：谁调、什么时候调、签名长啥样、region 自己持有啥状态。本节把四个方法逐一拆开讨论，最后汇总候选接口契约。

### 2.1 Display：什么时候画、画到哪里、画什么

**调用关系**：finder 的渲染入口是 `session.Display()`（被 owner `BufPane.Display` 调，bufpane.go:353）。目前 session.Display 一把梭完（边框 + 内容 + 预览），底盘化后这个总入口保留，但里面改成循环调各 region.Display。

**待拍板 D1：Display 谁调、何时调** ✓ **已定 D1.a**

| 候选 | 含义 | 评价 |
|---|---|---|
| **D1.a** | session.Display() 内循环 `for _, r := range regions { r.Display() }` | 单一渲染入口、单次绘制帧；session 仍是渲染权威；region 互不知道彼此 |
| D1.b | 每个 region 挂自己的 Redraw 钩子 | 解耦但乱；多 region 同时触发 Redraw 时序难控 |

**已定 D1.a**。维持单次绘制帧的现状。

**待拍板 D2：region 怎么知道自己的屏坐标** ✓ **已定 D2.a**

Display 要画到屏上，必须知道自己在哪。两种范式：

- **D2.a：session.Open() 期间构造 region，构造时塞 rect**。NewSession 返回空壳（无 region、无 rect）；session.Open(rect, ...) 拿到 owner pane 的 Rect 后，根据布局算出各 region 的子 Rect，构造 region 时塞进去。Region 用构造时塞入的绝对屏坐标 Rect 画，session 自己也持有 rect 做 mouse hit-test。Region 整个生命周期用这个 rect；close 后 region 随 session 一起销毁。
- **D2.b：region 自己持有 getter，session 调 Display 前后能查**。session 仍要算 rect，但它不存而是 region 存；session 通过 `region.Rect()` 查询（接口里加 Rect 方法）。

**已定 D2.a**。理由：
- rect 在 finder 生命周期内不变（运行中 resize → close，不重布局），Open 时一次算好即可
- session 是单次使用（Open 后靠 onClose 收尾，关闭后需重新 NewSession），rect 没有跨 Open 复用的必要
- session 和 region 都不需要「问对方 rect」的运行时协议
- Display 签名保持纯无参 `Display()`，接口干净

「构造时塞」明确为「session.Open() 期间构造 region、构造时塞入」。

**D2.a 总结**：session.Open() 期间，根据当时的 owner pane 屏面积大小决定 region 总数——能显示的全建，不该显示的不建（例如 history 在 `H<15` 或 history 为空时不建；preview 在 `W<10` 时不建）。每个被创建的 region 在构造时拿到自己的 rect，整个生命周期内 rect 不变。后续 `regions []Region` 切片长度是动态的（可能 1、2、3 个），所有遍历代码（Display 循环、hit-test）必须按切片长度而非硬编码 3 来写。

**待拍板 D3：Display 画的范围** ✓ **已定 D3.c**

| 候选 | 含义 |
|---|---|
| D3.a | region 只画自己矩形内的内容（含矩形内部所有分隔线、cursor）。session 只画 finder 外边框。 |
| D3.b | region 画矩形内 + 区间的分隔线（如 history 上沿 `─────`）。session 只画外框。 |
| **D3.c** | region 只画纯内容；所有线（外框、内部分隔符、分隔线列）都 session 画 |

**已定 D3.c**。理由：
- 分隔线是 finder 视觉骨架，不是任何 region 的「内容」
- 让 region 画线会导致线段计算散在多处（左右栏的 `│` 列、history 上沿的 `───`、外框的 `┌┐└┘─│`），改 layout 时要同步改多个 region
- session 是视觉骨架的权威，region 只管矩形内的字符内容
- session 画线时已经知道所有 region 的 rect 位置（regions/regionRects 都是它的），区域间的分隔线 / 分隔符列 / 外框交叉字符都能精准算

**具体职责切分**：
- session 画：外框（上 `┌──┐`、下 `└──┘`、左 `│`、右 `│`）、左右栏分隔符列的 `│`、区之间分隔线（如 history 上沿的 `─────` 和外框交叉字符 `┼`/`┬`/`┴`）
- region 画：自己矩形内的纯字符内容（文件名、目录名、breadcrumb、预览文本、history 路径等）

**Display 决议候选**：

```go
// session 在每帧 Display 链上调用。region 用构造时塞的 rect 画自己的内容。
// session 负责画外框 + 左右栏分隔符列 + 区之间分隔线。
Display()
```

### 2.2 HandleEvent：归属 + 签名

session 是事件入口。按归属规则转发：key → focus region；mouse → hit-test 命中的 region；resize / blur → session 内部拦截不外传。

**归属（已明确）**

**modal 打开时（先判）**：session.HandleEvent 入口第一步判 modal 状态——若 modal 激活，**所有事件**（key / mouse click / mouse move / 任意类型）一律进 modal 处理，region 收不到，session 全局键也跳过。这是底盘层的预留原则：现有 3 个 modal（add / delete / rename）走的是 micro 外部 `dialog.NewInputDialog`，由 micro 事件循环直接接管，不经 session.HandleEvent，当前无代码占用。后续若有内嵌 modal（如「确认删除 y/n」），按此原则走。

**modal 未开时**按基础归属：

| 事件 | 归属 |
|---|---|
| key | 喂给当前 focus region；region 不处理则 session 接管全局键（Esc 关、Ctrl-Q/q 退） |
| mouse click / wheel | hit-test 命中的 region（regions 平铺不重叠，命中唯一） |
| mouse move (Buttons==0) | 丢弃，不喂 |
| resize | session 拦截（运行中 resize → close(Resize)） |
| blur | session 拦截（等价 Esc） |

**待拍板 E1：region.HandleEvent 签名形状** ✓ **已定 E1.b**

| 候选 | 签名 | region 能 reject 否？ |
|---|---|---|
| E1.a | `HandleEvent(ev tcell.Event) bool` | 能，false = 未处理 |
| **E1.b** | `HandleKey(*EventKey) bool` + `HandleMouse(*EventMouse) bool` | 能，false = 未处理 |
| E1.c | `HandleEvent(ev tcell.Event)`（无返回） | 不能 |

**已定 E1.b**（拆 key / mouse 为两个独立方法）：
- 键盘与鼠标是两类**完全独立**的事件，类型上隔开更符合它们的语义
- region 不用写 `switch ev := ev.(type)` 大分支，HandleKey 只谈键、HandleMouse 只谈鼠
- session 按 ev 类型机械分发（key → HandleKey，mouse → HandleMouse），不关心 region 处理什么
- bool 返回保留：false = 「这个具体的 key / mouse 我不处理」 → session 可 fallback 到全局键

** E1.a vs E1.b 实际差别**：
- E1.a：方法合并为一个；region 自己 switch ev 类型；同一个 HandleEvent 里同时有键和鼠逻辑
- E1.b：方法分两个；session 帮你 switch；HandleKey / HandleMouse 各管一类，代码各居其位

** 去掉 E1.b 原表里的 `inRect bool`**：E2.a 已保证 session 只在 hit-test 命中时调 HandleMouse，到了 region 这一层 `inRect` 恒为 true。如果 region 二次判定可以自己查自己的 rect，session 不传额外参数。

**待拍板 E2：mouse 路由谁做** ✓ **已定 E2.a**

| 候选 | 含义 |
|---|---|
| **E2.a** | session 按 rect 表 hit-test，命中即喂 region |
| E2.b | 全部 mouse event 都喂给当前 focus region |

**已定 E2.a**。理由：
- 以 mouse 坐标为唯一依据：哪里点就哪里，逻辑最直接
- gap（分隭符列 / 分隭符行 / 外框）里的 mouse 返回 -1，session 干净 drop，不依赖任何 focus 状态
- 与 move 事件的 hit-test 路径一致——二者同一套坐标→region 映射，伪代码一致

**E2.a 的专属后果**：

- click / wheel 命中非 focus region 会触发 switchFocus 切过去（E2.b 才会“不切换”）；同区内击是 switchFocus 内部 no-op。这与 FFM 一致——该切就切、不该切就不切

**待拍板 E3：mouse move** ✓ **已定 E3.c**

| 候选 | 含义 | 留什么 / 丢什么 |
|---|---|---|
| E3.a | session 直接丢弃，不喂 | 丢；session 不知道 mouse 在哪个 region |
| E3.b | 喂给 region，由 region 决定 | 留全权限；本期无 region 需要（hover 提示） |
| **E3.c** | FFM 跨区切换：session 在 move 越过 region 边界时切 focus，同区内 move 忽略 | 拿焦点决策能力；其他全丢 |

**已定 E3.c**。mouse 驱动体验更顺手；鼠标滑到 fileList / historyList 之间不需要手动 click 就自动聚焦。**「鼠标滑到 preview 丢焦点」的旧担忧被 §2.6 补遗消除**：FFM 跨过 preview 时 `.(KeyboardRegion)` 类型断言拒收，`fm.focus` 不动，键盘仍按当前 focus 走——preview 不实现 `KeyboardRegion`，手滑鼠标不会丢焦点。

**FFM 一句话**：
> move 事件到达时，若 `hitTestMouse(e) != fm.focus` 且 `hitTestMouse(e) ≥ 0`，则切换 focus；否则不动。

`switchFocus` 内部对同 idx / -1 / 越界 都 no-op——这条伪代码一行同时覆盖：同区不变、跨区切换、进出 gap、点外框。伪代码在 §2.4。

### 2.3 FocusOn / FocusLost：焦点转移协议

**调用关系**：session 是焦点转移的唯一决策者，region 自身不能主动换焦点（焦点是 session 全局状态，避免竞争）。调用时机：

- **Open 后**：session 选定初始 focus region（沿用现状：fileList），调它的 FocusOn
- **mouse move 跨 region 边界时**（E3.c FFM）：move 命中非 focus region → 调旧 region.FocusLost() → 调新 region.FocusOn()
- **mouse click / wheel 命中非 focus region 时**：同上（击本区时 switchFocus 内 no-op）
- **close 时**：session 调当前 focus region.FocusLost() 清状态（防止下次 Open 残留视觉）

切换协议（伪代码已固定）：

- 顺序：先旧 region.FocusLost() → 更新 fm.focus → 新 region.FocusOn()；顺序错了会闪烁
- 跳过：to == fm.focus 或 to 越界 → no-op（防 click-to-same-region 浪费）

**所有键盘 event 一律只转发给当前 focus 的 KeyboardRegion**（C-2）。region 不处理则 session 接管全局键；region 不是 `KeyboardRegion`（如 preview）则在 key 分支类型断言时被拒，根本收不到键盘事件。session 同一个 `fm.focus` 变量同时承担「键盘走向」和「视觉高亮」两个职责——但**仅对 `KeyboardRegion` 而言**。preview 这类 non-key region 上，`fm.focus` 不指向它也就无关紧要。

**待拍板 F1：签名要不要带参数** ✓ **已定 F1.a**

| 候选 | 签名 | 含义 |
|---|---|---|
| **F1.a** | `FocusOn()` / `FocusLost()` 无参 | 最简单；region 收到回调时只能假定「焦点来/走了」 |
| F1.b | `FocusOn(prev Region)` / `FocusLost(next Region)` 带上下文 | region 可以知道从哪来/到哪去，可能用于「同区切换不重画」等优化 |

F1.b 潜在用途小（finder 切焦点频率极低），且接口一旦定下不容易改。**已定 F1.a**：无参、签名稳定。

**待拍板 F2：视觉变化的范围** ✓ **已定 F2**

| region | FocusOn 应该做什么 | FocusLost 应该做什么 |
|---|---|---|
| fileList | 设选中行 reverse 高亮（现状色 focus） | 改回未 focus 色（原色） |
| historyList | 设选中行 reverse 高亮（现状色 focus） | 改回未 focus 色 |
| preview | 空（无视觉可表达） | 空（无视觉可表达） |

**FocusLost 协议的**具体**用途以 fileList 为例**：从别的 region 跳走时，fileList 的反白光标要从「focus 色」调回「原色」。这个动作是 region 自己取定，session 不会跨 region 做——因此文件列表是 protocol 唯一需要 FocusLost/**FocusOn** 的具体用途。

**preview 与 focus 协议的关系（§2.6 补遗修订）**：原表述「preview 为何空」被 §2.6 推翻——preview **结构上不该有** FocusOn/FocusLost/HandleKey/KeyboardRegion() 四个方法（它不实现 `KeyboardRegion`）。preview 上不存在"focus 状态"，不是因为"没东西可调所以空"，而是 **Region/KeyboardRegion 接口分层的必然结果**。详细论证、类型升格路径、§2.4 接口契约修订均见 §2.6。

**待拍板 F3：要不要区分「首次 focus」和「再次 focus」** ✓ **已定 F3：不区分**

Open 时调 FocusOn 算首次 focus（文件列表初始光标落在首条目）；用户点 fileList 时再次 FocusOn（光标保持原位）。两种情况行为可能不同（首次需要初始化、再次只是视觉恢复），要不要 `FocusOn(init bool)` 区分？

**已定 不区分**。region 自己用内部状态判断（如 fileList 用 cursor 是否已初始化过）。签名保持无参。

**FocusOn / FocusLost 决议候选**：

```go
// session 在焦点进入本区时调。区域应在此调整视觉（高亮、cursor 位置等）。
// session 是唯一调用方，region 自身不能主动切换焦点。
FocusOn()

// session 在焦点离开本区时调。区域应在此清掉「被选中」视觉，恢复「未选中」外观。
FocusLost()
```

### 2.4 汇总：候选接口契约

把 D/E/F 三组决议合起来（§2.6 补遗后修订）：

```go
// Region 是 finder 内一个自管理区域的最小契约。
//   - 构造时 session 塞入绝对屏坐标 Rect（finder 生命周期内不变）。
//   - session 在每帧 Display 链上调用 Display() 画自己内容（不含框线）。
//   - session 按 hit-test 把 mouse 事件交给 HandleMouse；返回 false 表示「这个具体事件我不处理」。
//
// 接键盘事件的 region（fileList、historyList）还应实现 KeyboardRegion；preview 这类
// 不接键盘的 region 只需满足 Region。focus 管理、HandleKey 全部归属 KeyboardRegion 子接口，
// preview 在结构上不参与 focus 路由（见 §2.6 C-1..C-3）。
type Region interface {
    Display()
    HandleMouse(ev *tcell.EventMouse) bool
}

// KeyboardRegion 是接键盘的 Region。session 把键盘事件只送给当前 focus 的
// KeyboardRegion；FocusOn/FocusLost 是 session 切换 focus 时通知 region 的钩子。
// KeyboardRegion() 让 cycleFocus 知道此 region 参与轮转。
type KeyboardRegion interface {
    Region
    HandleKey(ev *tcell.EventKey) bool
    FocusOn()
    FocusLost()
    KeyboardRegion() bool
}
```

§2.5 单接口形态已被 §2.6 取代，旧展开以 §2.6 最终接口契约为准。

session 持有：

- `regions []Region`：所有区域
- `focus int`：当前 focus region 在 regions 里的下标
- `regionRects []Rect`：每个 region 的屏坐标（构造时算好，和 region 一一对应）

session 的事件分发骨架（伪代码，§2.6 补遗后修订）：

```go
func (fm *Session) HandleEvent(ev tcell.Event) {
    if _, ok := ev.(*EventResize); ok { fm.close(Resize); return }
    // blur 由 NotifyBlur 方法单独走，不经 HandleEvent

    switch e := ev.(type) {
    case *EventKey:
        switch e.Key() {
        case tcell.KeyTab:
            fm.cycleFocus(+1); return
        case tcell.KeyBacktab:
            fm.cycleFocus(-1); return
        }
        // C-2：键盘事件只送给当前 focus 的 KeyboardRegion。preview 这类 non-key region
        // .(KeyboardRegion) 断言失败，根本不会被问键。
        if kr, ok := fm.regions[fm.focus].(KeyboardRegion); ok && kr.HandleKey(e) {
            return
        }
        // 上面 false 走全场（region 返 false 或非 KeyboardRegion）：全局键接管
        fm.handleGlobalKey(e)
    case *EventMouse:
        idx := fm.hitTestMouse(e)
        if idx < 0 { return } // gap / 边框 的 click / wheel / move，直接丢
        // 对所有 mouse event 一视同仁——先喂 HandleMouse，再考虑 focus。
        // mouse move（Buttons()==0）以 HandleMouse 表现为 no-op（region switch 都返 false）；
        // 跨区切 focus 由下方 switchFocus 调用负责。
        fm.regions[idx].HandleMouse(e)
        // C-3：mouse→switchFocus 仅对 KeyboardRegion 生效，preview 命中不动 focus。
        if e.Buttons() == 0 {
            // FFM：mouse move 跨区切 focus（同区或 -1 由 switchFocus 内部 no-op）。
            // type 断言同时拦掉 preview（防止手滑鼠标丢失焦点）。
            if kr, ok := fm.regions[idx].(KeyboardRegion); ok {
                fm.switchFocus(idx)
            }
            return
        }
        // click / wheel 命中非 focus 区切 focus
        if kr, ok := fm.regions[idx].(KeyboardRegion); ok {
            fm.switchFocus(idx)
        }
    }
}

// cycleFocus：Tab/Shift-Tab 触发的 focus 轮转，过滤出 KeyboardRegion 跳过去。
// preview 这类 non-key region 被类型断言拦掉、轮转跳过。
func (fm *Session) cycleFocus(delta int) {
    n := len(fm.regions)
    if n == 0 { return }
    next := fm.focus
    for i := 0; i < n; i++ {
        next = (next + delta + n) % n
        if _, isKey := fm.regions[next].(KeyboardRegion); isKey {
            fm.switchFocus(next)
            return
        }
    }
    // 走到这里说明一个 key region 都没有（或现存 focus 本身就是唯一 key），no-op
}

func (fm *Session) hitTestMouse(ev *EventMouse) int {
    mx, my := ev.Position()
    // 顺序遍历即可：regions 平铺不重叠，找到第一个也是唯一一个
    for i, r := range fm.regionRects {
        if inRect(mx, my, r) { return i }
    }
    return -1
}

// C-3 运行期兑现：两端都必须是 KeyboardRegion，non-key region 上拒收。
func (fm *Session) switchFocus(to int) {
    if to == fm.focus || to < 0 || to >= len(fm.regions) { return }
    cur, ok1 := fm.regions[fm.focus].(KeyboardRegion)
    next, ok2 := fm.regions[to].(KeyboardRegion)
    if !ok1 || !ok2 { return }
    cur.FocusLost()
    fm.focus = to
    next.FocusOn()
}
```

伪代码变更点：

- `cycleFocus`：`KeyboardRegion() bool` → `.(KeyboardRegion)` 类型断言，语义等价但结构上“就是 KeyboardRegion”，不是“返回 boolean 哨兵”。
- `switchFocus`：入口加两端 `.(KeyboardRegion)` 断言，preview 这类 index 传入被拒。防 cycleFocus 以外代码（call site）接错。
- `HandleEvent` key 分支：`.(KeyboardRegion)` 断言后调 `HandleKey`。preview 这类没 KeyboardRegion 即不接键。
- `HandleEvent` mouse 分支：click / wheel / move 统一先 `regions[idx].HandleMouse(e)`，再以 `.(KeyboardRegion)` 守卫决定是否 `switchFocus`。preview 命中 focus 不动。
- FFM (`Buttons()==0`) 跨区切 focus：同上加断言，鼠标滑过 preview 不改 focus，从根上消除「手滑丢焦点」。

### 2.6 议题 1 补遗：focus 是 KeyboardRegion 的专属语义

**触发**：议题 1 §2.2/§2.3 把 `FocusOn`/`FocusLost`/`HandleKey`/`KeyboardRegion() bool` 挂在单接口 `Region` 上，`preview` 也实现它们但行为为空（「无视觉可表达」）。原 P6「preview 为何空」的论证已经默认了：空函数不是设计错位、只是没东西可表达。

但根本追问——**focus 对一个不接键盘的 region 意味着什么**？

剥到底层，focus 回答的问题只有一个——「键盘事件此刻送给谁」。这是**路由问题**，只对 keyboard recipient 有意义。一个 region 不接键盘，那"键盘送给谁"对它就是**空集**：路由表是个 keyboard-recipient 的索引，不在表里的元素没有「焦点状态」可言，进不去也出不去，不影响输入流也不影响输出流。给它 `FocusOn`/`FocusLost` 不是「功能空」，是**类型系统给了一个无取值空间的字段**。

由此推出三条 chassis 不变量，**贯穿议题 1 的所有步骤**：

- **C-1（接口分层）**：`FocusOn` / `FocusLost` / `HandleKey` / `KeyboardRegion() bool` 全部归属 **`KeyboardRegion` 子接口**，`Region` 接口只含 `Display` + `HandleMouse`。`preview` 只实现 `Region`；`fileList` / `historyList` 实现 `KeyboardRegion`。
- **C-2（键盘路由）**：键盘事件只送给当前 focus 的 `KeyboardRegion`。session 在 key 分支对 `regions[fm.focus]` 做 `.(KeyboardRegion)` 类型断言，不成立就不接键。
- **C-3（mouse 不动 non-key focus）**：mouse 命中 region 后，`regions[idx]` 若是 `KeyboardRegion` 才动 `switchFocus`；若不是 `KeyboardRegion`（如 preview），永远不动 focus，只调 `HandleMouse`。

**对议题 1 原论证的修订**：

| 部位 | 原表述 | 新表述 |
|---|---|---|
| §2.3「preview 为何空」 | preview 没有选中、无光标、FocusOn/Lost 无可表达，所以空 | preview **结构上不该有** FocusOn/Lost（它不实现 `KeyboardRegion`）。不是「空」，是**没有这俩字段** |
| §2.3「session 同一个 focus 变量同时承担键盘走向和视觉高亮两个职责」 | 隐含适用于所有 region | 仅适用于 `KeyboardRegion`。preview 这类 non-key region，focus 字段对它没有意义 |
| §2.3「所有键盘 event 一律只转发给当前 focus region」 | "focus region" 套到所有 region | "所有键盘 event 一律只转发给当前 focus 的 `KeyboardRegion`"（C-2） |
| §2.4 接口契约 | `Region` 5 方法（含 FocusOn/Lost/HandleKey/KeyboardRegion()） | `Region` 2 方法 + `KeyboardRegion extends Region` 4 方法（见末尾"最终接口契约"） |
| §2.4 `cycleFocus` | `regions[next].KeyboardRegion()` boolean 哨兵 | `regions[next].(KeyboardRegion)` 类型断言——**语义等价但类型更直接** |
| §2.4 `switchFocus` | 两端都 `FocusLost` → 改 focus → `FocusOn`，无类型守卫 | 两端加 `.(KeyboardRegion)` 断言——non-key region 上拒收（C-3 运行期兜底） |
| §2.4 `HandleEvent` mouse 分支 | `switchFocus(idx)` 无条件 | `if kr, ok := regions[idx].(KeyboardRegion); ok { switchFocus(idx) }`——preview 命中 focus 不动，只喂 `HandleMouse`（C-3） |
| §2.4 mouse move FFM | "move 越 region 边界切 focus" | `Buttons()==0 && hitTest≥0 && regions[hitTest].(KeyboardRegion)` 三条件都满足才切（防鼠标滑过 preview 切到 preview） |
| §6 preview 整节（P1「preview 是 Region 与 fileList 平级」、P6「preview.FocusOn/Lost 空」） | 「接口平级各填各的空」 | preview **不存在** FocusOn/Lost 方法；按"接不接键盘分层"，preview 与 fileList 是不同接口层级 |

**类型升格论证**：若未来 `preview` 接 PageUp/Down 翻页（F10 中 P8 暂不做），**不是给 `Region` 补 `HandleKey`**（让 Region 接口被"可能接键盘可能不接"两类 region 污染），而是 `preview` 升级实现 `KeyboardRegion`（**结构升格**）。这条原则不松动，「接不接键盘」二分不出现中间态。

**FFM 在新原则下的归宿**：原本 §2.2 E3.c 的「鼠标滑到 preview 丢焦点、键盘落到 preview 被吞——频率低后果轻微」在新原则下不存在——FFM 跨过 preview 时类型断言直接拒，`fm.focus` 不动，键盘路由仍按当前 focus 走，「手滑丢焦点」这条 UX 退化直接消除。FFM 仍可启用（UX 选择），但只在 KeyboardRegion 之间切换。

**最终接口契约（§2.4 修订）**：

```go
type Region interface {
    Display()
    HandleMouse(ev *tcell.EventMouse) bool
}

type KeyboardRegion interface {
    Region
    HandleKey(ev *tcell.EventKey) bool
    FocusOn()
    FocusLost()
    KeyboardRegion() bool
}
```

## 三、议题 2：布局职责（rect 谁算） ✓ **已定 L1**

### 3.1 候选方案

| 方案 | rect 来源 | 谁算 | 谁持有 | 已定 |
|---|---|---|---|---|
| **L1** | session 在 Open 时算好，构造 region 时塞进去；region 自己持有 | session | region（构造时注入，不可变） | ✓ |
| L2 | region 自己根据总可用区域协商 | region 协商 | region | — YAGNI |
| L3 | session 算、region 只管画收到的矩形 | session | session（每个 Display 调用传入） | — 互斥 |

### 3.2 评估

- **L1**：session 是布局权威（算 rect）；region 拿到的 rect 是不可变事实（构造时塞进、生命周期不变、靠 D2.a 限定）。简单、单一职责。Display() 无参（议题 1 已定）——region 必须自己知道 rect。
- **L2**：region 自管理，看上去对将来加新 region 友好。但「协商」机制复杂——两个 region 抢同一片空间怎么办？需要协议。这些复杂度该出现时再制造（YAGNI），现在唯一需要的「加新 region」场景是 history（议题 3）——L1 同样能插入。
- **L3**：与 Display() 无参互斥（没地方拿 rect）。被技术选择隔要打消。

**已定 L1。** **构造时定死 rect，无需 setter。**

依据：

- D2.a 已定：session 在 Open 期间构造 region、构造时塞 rect、生命周期内不变
- finder 运行中 resize 不重布局（Resize 事件 → close）
- session 是单次使用（NewSession → Open → close）

### 3.3 rect 计算一览

## 四、议题 3：history 区在底盘里的位置与交互

历史（history）是底盘的第一个新区域，要回答：

- **位置**：在左栏底部，占多少行？
- **显示条件**：什么时候不画？
- **键盘交互**：选中 / 切换目录的键位

这些是 history 自身的属性，但它们会影响 layout 计算（议题 2 已定 L1，议题 3 详谈 historyRect）。

### 4.1 位置与高度 ✓

history 块 = **上边框线（1 行）+ 内容区（3 行）+ 下边框线（与 finder 外框下边框共享，不多占行）= 4 行**。位于左栏 hint 行下方、外框下边框线上方。

```
┌─── Open File ─────┬──────────────────┐   ← finder 外框上边框（y=0）
│ 面包屑             │                  │
│ 文件 1  ◀          │                  │
│ 文件 2            │   preview        │
│ ...               │                  │
│ hint (perms/size) │                  │
│ ────────────────── │                  │   ← history 上边框（独立 1 行，session 画）
│ 历史 1  ◀          │                  │   ← history 内容区 3 行（滚动窗口，region 画）
│ 历史 2            │                  │
│ 历史 3            │                  │
├───────────────────┴──────────────────┤   ← finder 外框下边框 = history 下边框（共享同一行）
                                        statusLine
```

**下边框共享**：history 的下边框线 就是 finder 外框的下边框线，同一条横线。session 画外框下边框时左边那一段同时作 history 下边框。

**边框归属（D3.c）**：

- 上边框线、finder 外框下边框线（含 history 下边框这一段）：session 画
- history 内容区 3 行：history region 画

### 4.2 显示条件 ✓ **已定 H2**

**门槛候选**：

- (H1) H < 15 不显示（沿用 F10 brainstorm）
- (H2) H < 15 **且** history 为空时不显示（叠加条件） ✓

**已定 H2**：H < 15 不显示（窄屏让位给文件列表）；history 为空不显示（全新安装没必要画空块）。

D2.a 联动：以上任一不满足，则不构造 history region（fm.regions 只含 fileList + preview）。

### 4.3 layout 数学 ✓

rect.H ≥ 15 且 history 非空时：

```
contentH         = rect.H - 1(statusLine) - 2(border)   // = 12（H=15 时）
historyContentH  = 3                                       // 内容区固定 3 行
historyH         = 1(上边框) + 3                           // = 4（不包含与外框共享的下边框）
fileListArea     = contentH - historyH                     // = 8（H=15 时）
fileRows         = fileListArea - 2(面包屑+hint)           // = 6（H=15 时）
```

即 H=15 时文件列表还剩 6 行（面包屑 + 6 + hint）。

rect.H < 15 或 history 为空时：不构造 history，fileListArea = contentH = 12，fileRows = 10。

### 4.4 滚动行为 ✓

history region 内部管理 scroll offset：实际 history 总数可超过 3，渲染窗口限在 3 行，scroll offset 决定看到的是哪 3 条。参照 micro 原生 `dialog.NewSelectDialog` 的 `maxVisible` + `ensureVisible` 模式：

- `scrollOffset int`：当前显示窗口顶部对应 history 索引
- 渲染时只画 history[scrollOffset..scrollOffset+3] 的 3 条
- 光标 Up/Down 时调 `ensureVisible(cursor, scrollOffset)`，必要时调 scrollOffset
- 滚动只在 history 列表 > 3 时有实际效果（len ≤ 3 时不用管）

### 4.5 键盘交互 ✓

**全局规则**：除 Tab/Shift-Tab 之外，没有键盘事件能切换 focus region。上下键仅负责当前 focus region 内的光标移动，不跨界。

history 区自己的 `HandleKey`：

- Up/Down：移 history 光标 ±1（**clamp，不跨界**）
- Enter / Right：切到该目录
- wheel 上下滚：移 history 光标 ±1
- **Esc / Ctrl-q / 其他键**：由 session 处理（关 session 等），不归 region

**跨界上下键问题（已澄清）**：光标在 fileList 末行按 Down → clamp 在末行；需 Tab/Shift-Tab 才切到 history。连续体感不是该走上下键实现的，Tab/Shift-Tab 是唯一键盘换区路径。

session 调度逻辑（§2.6 补遗后修订）：

- 鼠标落在 history 区 → HandleEvent 喂给 history，session 同步调 history.FocusOn()、fileList.FocusLost()（preview 不参与——它不实现 `KeyboardRegion`）
- 鼠标落在 fileList 区 → 喂给 fileList，同步切焦点
- 鼠标落在 preview 区 → 喂给 preview.HandleMouse；focus 不动（preview 不实现 `KeyboardRegion`，C-3 类型断言拒收）
- 键盘事件只喂给当前 focus 的 `KeyboardRegion`；只有 Tab/Shift-Tab 例外（session 拦截后调 cycleFocus）

### 4.6 session 焦点切换的触发 ✓

议题 1、议题 2、议题 5 阶段陆续收敛出**两个触发渠道**，本节明文记录：

| 触发方式 | 实现 | 决议 |
|---|---|---|
| mouse hit-test（FFM） | mouse 事件 hit → switchFocus（议题 1 E3.c） | ✓ |
| 键盘 Tab / Shift-Tab | session 拦 Tab/Backtab → cycleFocus 跳过 non-key（议题 1 F4） | ✓ |

**规则**（§4.5）：除 Tab/Shift-Tab 外，**任何键盘事件都不能切换 focus region**。上下键仅限当前 focus region 内光标移动（clamp / wrap 由 region 决定），跨区唯一路径是 Tab/Shift-Tab。

## 六、议题 5：preview 区在底盘里的角色（§2.6 补遗后修订）

原 §6 全文依据「preview 是 Region、与 fileList/historyList 平级、FocusOn/Lost 空」三条原则。§2.6 补遗后全部修订。

### 6.1 关系定型

- `preview` 实现 **`Region` 接口**（`Display` + `HandleMouse`），**不实现 `KeyboardRegion`**
- `fileList` / `historyList` 实现 **`KeyboardRegion` 接口**（`Display` + `HandleMouse` + `HandleKey` + `FocusOn` + `FocusLost` + `KeyboardRegion()`）
- preview 与 fileList/historyList **是同一个 `regions []Region` 切片里的兄弟**（session 中以同一种结构调度），但**接口层级不同**——按「接不接键盘」二分

这一修正不是「在原来上额外拆接口」（AGENTS.md「如非必要勿增实体」原则），而是**对 §2.2 §2.4 原"5 方法单接口"设计的修订**——按新原则（§2.6 C-1）5 方法本就不该全平。

### 6.2 preview 行为

- `preview.Display()`：画当前选中文件的内容（等价为现状 `drawPreview`）
- `preview.HandleMouse(ev) bool`：接 WheelUp/Down → scroll + Redraw + return true；其余（click、其他按钮）→ return false
- preview **没有** `FocusOn` / `FocusLost` / `HandleKey` / `KeyboardRegion()` 这四个方法——结构上不存在，编译期拒收

### 6.3 类型升格路径（不是补接口）

若 P8 后续要让 preview 接 PageUp/Down 翻页，正确做法是 `preview` 升级实现 `KeyboardRegion`（结构升格），不是给 `Region` 加 `HandleKey`。理由：让 `Region` 接口被"可能接键盘可能不接"两类 region 污染，逆推§2.6 C-1 「接不接键盘二分」的核心原则。

### 6.4 preview 与 focus 路由

按 §2.6 C-2 / C-3：

- mouse 命中 preview → session 只调 `preview.HandleMouse`；`fm.focus` 不动
- FFM 跨过 preview → `.(KeyboardRegion)` 断言拒收，`fm.focus` 不动
- 旧「鼠标滑到 preview 丢焦点、键盘落到 preview 被吞（§2.2 E3.c'频率低后果轻微'）」在新设计下不存在，UX 退化从根上消除

### 6.5 P1..P6 旧决议的对应修订

| 旧决议（§8 表） | 修订后 |

## 七、议题 6：实施拆分 ✓

### 7.1 两步走 ✓

| 步骤 | regions 数量 | 含义 | 验证标准 |
|---|---|---|---|
| **Step 1（底盘 PR）** | 2 个（fileList + preview） | `session.go` 拆出 + `fileList.go` 抽成 Region + `preview.go` 抽成 Region | 纯重构，**行为零变化**（fileList/preview 现有所有交互、视觉、边界 case 不变）。代码里**完全没有 history 这个概念**。 |
| **Step 2（history PR）** | 3 个（+ historyList） | `historyList.go` 加成第 3 个 Region + 记录端（`config.RecordDirHistory` + buffer 挂钩） | history 端到端可用：切换目录后下次起动能看到记录 |

**Step 1 的硬限制**：

- `regions []Region` 长度 = 2，不为 history 预留位置、不设占位、不加 history 判断
- session.Open() 只构造 fileList + preview，不留 historyRect 计算、不留 H<15 / len(history)>0 这种门槛逻辑
- Tab/Shift-Tab 轮转在 Step 1 仅 fileList 一个 key region，表现为 no-op（不需任何说明）
- 议题 3 全部内容（history 位置 / 高度 / 滚动 / 显示条件 / 键盘交互）都是 Step 2 的范围，**不提前出现在 Step 1**

**为何记录端跟 history 区域走**：Step 1 完全没有 history 这个概念（不构造、不预留、不占位）。如果把 history 区域和记录端拆成两 PR，中间状态是「history 区域已构造、但记录端未上——区域画个空 3 行」，对用户没意义。捆绑以后 Step 2 上线即端到端可用。

### 7.2 拆分依据

- **Step 1 是重构型**：diff 会比较大（session.go 拆开），但验收标准明确——fileList/preview 的所有现有行为不变，是「以纯重构提供 chassis 接口」
- **Step 2 是增量型**：在已稳定 chassis 上加一个 Region + 一个记录端，diff 小，review 友好
- **不拆三步**：记录端与 history 强耦合（history 没数据就空）、不能独立验证「记录端有没有进 history」，拆了会增加额外 PR 不收益

### 7.3 为何不选 S2 / S3

- S2 / S3 都会让 Step 1 diff 更大、review 更累；中间状态不可验证
- 拆成两步的代价是「等两个 PR 才看到 history」，但这个代价换取「每个 PR 独立可验证」
