# 怎么让编辑器跟 OpenCode 通信 —— AIBP 协议是怎么定出来的

microNeo的主要功能就是能和不同的 AI agent 通信。那么第一件事情就是要定义它们之间的通信协议。

---

## 1，协议要「agent 无关」

原因很简单：有人喜欢用 pi，有人喜欢用 opencode，还有人喜欢 claude code、codex、gemini cli……我们的通信协议应该是通用的，各AI agent只要支持这个协议就能直接参与通信。

设计原则：**协议里不出现任何 agent 特有的概念。**， N 端对 M 端的去中心化契约结构：

```
┌─────────────────────┐
│  发送端（编辑器）    │     ← 不知道 agent 内部实现
│  采集·组装·发现·发  │
└──────────┬──────────┘
           │  AIBP 协议
   ┌───────┼───────┐
   ▼       ▼       ▼
 pi 扩展 opencode claude ...
   ▲       ▲       ▲
   └───────┴───────┘
   每家按协议实现
```

新 agent 接入 = 在「接收端」那一栏多挂一个实现，**microNeo 不改一行代码**。

## 2，报文协议

协议里**只有一种**报文，叫 `context`：

```json
{
  "v": 2,
  "type": "context",
  "sender": { "pid": 54321, "name": "microNeo", "instance": "default" },
  "ts": 1717000123.456,
  "payload": {
    "path": "/Users/me/a.md",
    "cursor": { "line": 42, "col": 8 },
    "selection": { ... },
    "message": "这段标题感觉怪，帮我换个说法"   ← 关键字段
  }
}
```

**报文 payload 字段讲解**：

| 字段 | 必需 | 作用 |
|---|---|---|
| `path` | ✅ | 文件绝对路径。LLM 工具链（sed / ripgrep）天然对齐 |
| `cursor` | ✅ | 光标位置 `{line, col}`，1-based（行/列都从 1 起）|
| `selection` | ❌ | 选区 `{start, end, text}`。无选区则**整个字段省略**（不是 `null`）；`text` 也可省略（按行数阈值，详见 `说明-发送端.md §3.3`）|
| `message` | ❌ | 用户附的一句话。**有无决定接收端走哪条路径**——有则触发对话回合，无则作为「待用上下文」暂存 |
| `visible_lines` | ❌ | 可见区域文本。当前版本不发送（隐私考虑）|

坐标一律 1-based：跟 LLM 工具链天然对齐，发送端不用做 ±1 转换。**发送端保证合法，接收端不校验**——这是协议契约的一部分，也是在坚持「能力差异由接收端吸收」。

报文里其它位置上的字段：

- `v`：主版本整数（当前 `2`），从 `aibp.Protocol` 派生
- `type`：报文类型，当前只有 `context`
- `sender.pid` / `sender.name` / `sender.instance`：发送端标识，`name` 固定 `"microNeo"`，`instance` 当前 MVP 固定 `"default"`
- `ts`：发送时刻，Unix 浮点秒（毫秒精度）

## 3，通信协议

报文协议只回答「发送什么」，这一章要解决的是「怎么送过去」。场景并不复杂：microNeo 和 agent 在同一台机器上运行，但由用户分别启动；双方没有父子进程关系；一台机器上还可能同时运行多个 agent session。

基于这些条件，我比较了几种本地进程通信方案：

| 可选方案 | 优点 | 缺点 |
|---|---|---|
| stdin/stdout | 最直接，不用创建额外服务；读写接口所有语言都有 | 必须由一方启动并持有另一方进程；agent 的 stdin/stdout 已经被 TUI 占用，microNeo 也不应该接管 agent 生命周期 |
| localhost TCP | 跨平台、跨语言，工具和调试手段成熟 | 每个接收端都要分配端口，需处理端口冲突；还会把纯本机 IPC 变成网络监听，需要额外考虑暴露范围和访问控制 |
| HTTP | 请求边界、错误码和调试工具都很完善，未来扩展接口也方便 | 本质上仍要管理 TCP 端口；为偶尔发送一条 JSON 启动 HTTP server、处理路由和 header，明显太重 |
| 文件 + 轮询 | 实现门槛低，报文落盘后也容易人工查看 | 要在延迟和轮询频率之间取舍；还要处理半写文件、重复消费、并发覆盖、磁盘 IO 和僵尸文件 |
| Unix domain socket | 不需要端口；只在本机开放；可以直接用目录和文件权限控制访问；Go、Node 都原生支持 | 主要面向 Unix 系统；需要清理崩溃后残留的 socket 文件；部分系统还有 socket 路径长度限制 |

stdin/stdout 最大的问题不是技术上不能用，而是它要求 microNeo 和 agent 形成父子进程关系。实际使用方式正好相反：用户先在一个终端里打开 pi 或 OpenCode，再在另一个终端里打开 microNeo。编辑器不拥有 agent，也不应该为了发一条消息去重新启动它。

TCP 和 HTTP 能解决这个问题，但会带来端口。多个 agent session 同时运行时，每个 session 都要找一个空闲端口，再把端口告诉发送端。端口还意味着网络监听和访问控制。对于只在同一台机器、同一用户之间传递编辑上下文的功能，这些成本没有带来对应收益。

文件轮询看起来最省事，真正实现后却会把通信问题变成状态同步问题：发送端什么时候算写完，接收端什么时候算消费过，两个发送端同时写怎么办，接收端崩溃后旧文件由谁清理。为了发送一条低频消息维护一套轮询状态，不划算。

最后选择 **Unix domain socket**，是因为它刚好落在中间：像 TCP 一样支持彼此独立的进程和跨语言通信，却不需要端口；像文件一样可以用路径命名和权限隔离，却不需要轮询。每个 agent session 监听自己的 socket，microNeo 找到目标路径后直接连接即可。

它当然不是没有代价。AIBP 当前因此主要支持 macOS 和 Linux，接收端异常退出时也可能留下 socket 文件。但这两个问题的边界都很明确：平台支持可以以后增加新的 transport，残留文件则由注册发现阶段顺手清理。相比之下，Unix socket 让当前版本最重要的本地、多进程、低频通信保持了足够简单。

## 4，注册机制

选定 socket 以后，新的问题马上出现了：**发送端怎么知道 socket 在哪里？**

把路径写死当然可以，但这会立刻失效。用户可能同时开着多个 pi session、多个 agent，socket 还应该随用户隔离，不能让不同用户看到彼此的接收端。为此，AIBP 没有引入一个常驻的 registry daemon，而是用一个目录充当注册表。

目录算法很短：

```
base = $XDG_RUNTIME_DIR ? $TMPDIR ? /tmp
dir  = base + "/aibp-" + $UID
```

两端各自计算同一个路径。接收端把自己写进去，发送端扫描出来。目录放在 runtime / tmp 下，重启后自然清空；目录权限是 `0700`，socket 文件是 `0600`，不会把本机通信变成公开服务。

每个接收端对应两份文件：一个注册描述，一个 Unix socket。比如名为 `Alpha` 的接收端会生成：

```
ai-Alpha.json
ai-Alpha.sock
```

JSON 文件只描述「去哪儿找我」：

```json
{
  "name": "Alpha",
  "pid": 12345,
  "transport": "unix",
  "socket": "/tmp/.../aibp-501/ai-Alpha.sock",
  "protocol": "aibp-2.0",
  "startedAt": 1717000000,
  "cwd": "/Users/me/project",
  "labels": ["default"]
}
```

这里特意把 `name` 放进注册文件，也放进文件名。发送端只扫描 `ai-*.json`，不会误读目录里的其他临时文件；`pid` 用来判断进程是否还活着；`cwd` 和 `labels` 暂时只是给未来的项目筛选、多目标选择预留。

接收端启动时的顺序也有讲究：

1. 创建注册目录。
2. 选择一个名字。
3. **先监听 socket，再写 JSON 注册文件。**
4. session 结束时关闭 server，删除 JSON 和 socket。

如果反过来先写 JSON，再启动 socket，中间就会出现一个「看起来在线、实际上没人接」的假接收端。先 listen 后登记，注册表里的条目从出生起就尽量可用。

发送端发现时不会盲信文件。它会读取注册表，检查协议主版本，然后用 `DialTimeout` 试探 socket。能连上，才算真正存活。连不上时再检查 `pid`：进程已经死了，就顺手删除注册文件。这就是 GC。

```
注册文件存在
      ↓
协议兼容？──否──→ 跳过
      ↓ 是
socket 能 connect？──是──→ 返回 live receiver
      ↓ 否
PID 还活着？──是──→ 暂留，等待下次发现
      ↓ 否
删除僵尸注册文件
```

这个设计里没有中心服务，也没有谁维护一份内存中的全局列表。注册表只是临时目录里的事实快照，真正的存活判据是 socket 能不能连上。接收端加一个实现时，microNeo 不需要新增 agent 名称判断；它只要按照同一套规则注册，自己就会出现在发现结果里。

## 5，协议版本号 and 强制更新机制

版本号最初看起来只是一个整数，后来我发现它其实是在回答一个很现实的问题：**两端都能找到对方，但找到的版本还能不能通信？**

AIBP 使用两种形式表达同一个协议版本：

- 注册文件写完整字符串，例如 `"aibp-2.0"`，方便人和诊断工具阅读。
- 报文信封写主版本整数，例如 `"v": 2`，接收端收到一行 JSON 后可以快速判断是否接受。

主版本和次版本的意义不同：

| 版本变化 | 含义 | 处理方式 |
|---|---|---|
| major：`aibp-1` → `aibp-2.0` | 报文结构、语义，或者两端必须同步的实现约定发生不兼容变化 | 不能通信，必须升级其中一端 |
| minor：`aibp-2.0` → `aibp-2.1` | 增加可选字段或能力，旧端仍能理解原有报文 | 保持通信，未知字段忽略 |
| npm 包：`1.0.4` → `1.0.5` | 不影响跨端契约的实现层 bug 修复 | 不一定改变协议号，但应能单独更新 |

这里最容易混淆的是：**协议版本不是 npm 包版本**。`aibp.protocol` 表示「能不能按同一份契约说话」，`package.json` 的 `version` 表示「这份实现是哪一个发布包」。如果只是修了 socket 清理 bug，就不应该为了触发更新把协议从 `aibp-2` 硬升成 `aibp-3`。

但也有一种例外：报文格式没变，协议号仍然可能必须升 major。比如我把注册表目录从旧名字改成 `aibp-<UID>`。这不是报文字段变化，可是发送端和接收端如果不同时换目录，就会各自在不同的目录里找人，通信照样断掉。凡是升级过程中要求两端同步切换的实现约定，都属于协议级 breaking change。

版本检查分两道：

1. microNeo 扫描注册表时读取 `protocol`。主版本不兼容的 receiver 直接跳过，避免把报文发给一个「看起来在线、实际读不懂」的扩展。
2. receiver 收到报文后检查信封里的 `v`。主版本不匹配就忽略，不把未知版本当成当前版本处理。

如果 receiver 版本比 microNeo 旧，发送端不能假装一切正常，而是应该明确告诉用户：扩展需要更新。如果 receiver 版本更新，microNeo 也不能擅自降级对方，只能提示 microNeo 自己升级。这是一个单向通信系统里最简单、最可预测的协商方式。

「强制更新」的含义不是每次启动 microNeo 都偷偷联网，而是**协议不兼容时不继续发送，并把修复动作变成明确的用户操作**。当前的自举流程由 `microneo --check-agent` 触发：

```
检查 agent 是否安装
        ↓
读取扩展 package.json 的 aibp.protocol
        ↓
未安装 / 损坏 → install
协议主版本过旧 → update / reinstall
协议主版本过新 → 提示升级 microNeo
版本一致 → ready
```

这个流程还解释了为什么需要另一个 `microneo --update-aibp`。`--check-agent` 解决的是「两端能不能通信」；它不应该把每一次协议体检都变成包管理器。`--update-aibp` 解决的是「在协议兼容的前提下，接收端实现是不是最新」：opencode 的缓存不会主动刷新，就由 microNeo 清缓存后重新安装；claude 交给自己的插件管理器更新；pi 有自己的更新提示，microNeo 不插手。

最后一个取舍是：更新成功不等于当前 agent 进程已经加载了新代码。扩展通常要在下一次 session 启动时重新注册，所以更新流程负责把磁盘上的实现拉到正确版本，重启接收端则负责让新版本真正进入运行态。把这两件事分开，反而比试图从 microNeo 远程控制每个 agent 更可靠。

## 6，写协议最难的，是知道「什么不写进协议」

回过头看，AIBP 真正在做的事情是**画边界**：

| 协议**规定** | 协议**不管** |
|---|---|
| 注册表目录算法、文件 schema | agent 用什么扩展机制实现 |
| 传输（Unix socket、逐行 JSON）| agent 收到后具体怎么递送 LLM |
| 报文 schema、版本号 | UI 怎么呈现（输入框、status bar、widget…）|
| 递送语义（message 有无）| 冲突处理（agent 正在 streaming 怎么办）|
| 接收端契约（4 条规则）| agent 的名字怎么生成（参见 D11 名字池）|

每条「不写进协议」背后都是一个权衡：

- **不写 UI** —— pi 用 `setEditorText` 填入输入框，opencode 可能有自己原生的输入通道。协议强求「填输入框」就把 opencode 锁死
- **不写冲突处理** —— 当前协议是单向通信，没有「我问你是否在 streaming」的反向通道。强制排队 / 强制打断都是「协议替接收端做选择」
- **不写名字生成** —— 名字是「人类可读的 ID」，跟协议本身没关系（D11 单独设计）

**画完这条边界，整个协议就 1 个报文类型、4 个接收端义务、一个目录算法、一个版本字符串。** 没了。

协议设计就是这样——大头不花在「怎么写」，花在「决定不写什么」。剩下的就是体力活。
